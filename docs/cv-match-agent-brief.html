    Business problem · Current process

    Every request means reading the same CVs again

    Project leads and bid teams ask for people by skill, experience and language. Matching them against the team is done by hand.

    How a request is handled now

    1. Request arrivesFree text by email, often with "or" options and vague wording.
    2. Check who is availableFor simple, single-person requests: filter by availability first.
    3. Read CVs against every requirementFor complex requests (5–10 people, availability optional): all 80 CVs.
    4. Weigh trade-offs from memoryWho is strong where, who covers what, who is senior enough.
    5. Send a shortlist to interviewsOr add profiles to an RFP answer.

    Friction

    • Slow and repetitive. The same CVs are re-read for every request.
    • Wording mismatches. A request says "K8s", a CV says "container orchestration".
    • Depends on memory. Good fits are missed, especially less visible people.
    • Hard to show your reasoning to the requester.

    Business problem · Example

    A real request: four fullstack profiles for an RFP

    Incoming request · RFP bid teamAnonymised

    …we would need four developer profiles, that we can add to the RFP answer as part of the exemplary team. They don't have to be available; we would like to present the best in class we have. Can you please provide us with some Fulldstack developer sample profiles?

    Experience more than 5 years in this area, mix of seniority (2 more junior, 2 more senior) would be great. German/English required. Tech Skills see below.

    TechSkills

    • Java or Python
    • Frontend Typescript/Angular
    • Apache Spark, Spark SQL or similar
    • Data-Pipeline-Development
    • ETL-/ELT-Processes
    • REST-APIs or Webservices
    • Git-based Development, incl. Branching, Merge Requests or Pull Requests and Code Reviews
    • Containers, Kubernetes or Cloud-/Private-Cloud-environments
    • AI Skills would be great, focus on tooling throughout SDLC

    Would be great you could help us out once more. Let me know in case of any question.

    What makes it hard

    1. Four people, not one, and they have to work as a team.
    2. Nine skill lines with "or" and "similar". Many valid combinations, no clear priority.
    3. A built-in tension. "More than 5 years" and "2 more junior" need interpreting.
    4. Availability doesn't filter anyone out, so the whole group has to be reviewed.
    80 CVs × 9 skill lines=720judgments, by hand, for one request

    Agent design

    What the agent does

    It recommends and you decide. Each step is visible and can be corrected.

    1. Step 1

      Read the request

      Takes the request as it arrives: email text, RFP excerpt or a skill list.

    2. Step 2 Key step

      Triage the requirements

      Decides what is probably key, what is a nice-to-have, and where alternatives are acceptable. Asks when something is unclear.

    3. Step 3

      Check availability

      Reads availability from the planning system when the request needs it. Skips this step when it doesn't, as in the RFP example.

    4. Step 4

      Score every CV with evidence

      Scores each person per requirement and quotes the CV text behind it. No evidence, no credit.

    5. Step 5

      Build the team

      Ranked shortlist per role, a proposed team combination, and gaps such as "nobody has Spark and 10+ years".

    6. Step 6

      Hand over to you

      You review, adjust and approve before anyone is contacted or proposed.

    Why an agent

    A keyword search can't interpret vague requests, weigh must-haves against nice-to-haves, map synonyms and similar technologies, infer seniority from project history, explain its reasoning, or ask a clarifying question.

    Team shape

    4 profiles: 2 senior, 2 less senior. The agent fills each slot separately.

    Availability

    "Don't have to be available". The agent skips the availability check and searches all 80.

    Clarifying question

    "More junior" with 5+ years: should I read this as about 5–8 years vs. 10+ years?

    MVP scope

    What's in and what stays out

    The agent reads and recommends. It never acts on people or records.

    In scope
    • +Read requests in any formatEmail, RFP text, skill lists
    • +Triage requirementsKey, nice to have, baseline, accepted alternatives
    • +Availability check AddedRead-only connection to the planning system, used only when the request needs it
    • +Match all CVs with cited evidenceScore per person and per requirement
    • +Propose a team and report gapsRanked shortlist per role or seniority slot
    • +Ask clarifying questionsWhen the request is ambiguous or contradictory
    Out of scope
    • −Contacting peopleNo emails, invites or messages to candidates or requesters
    • −Changing HR recordsNo writes to CVs, HR or planning systems
    Always with a human

    The final selection, and anything that goes to a client or to interviews.

    Stretch · Risks and constraints

    Risks and how we handle them

    • Personal data (GDPR)

      CVs and availability are personal data. Use an approved tool and data location, limit access to the resource manager, inform employees and the works council where needed.

      High

    • Bias in matching

      Only skills, experience and languages count. Name, age, gender, nationality and photo are ignored or removed before matching.

      High

    • Hallucinated skills

      A model may claim skills a CV doesn't show. Every match cites CV text, and a human reviews the shortlist.

      Medium

    • Outdated CVs

      Results are only as good as the CVs. The agent flags old CVs, which helps keep them current.

      Medium

    • Over-reliance

      The shortlist could be taken as final. It is a decision aid. Selection stays with the resource manager.

      Medium
